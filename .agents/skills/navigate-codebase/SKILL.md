# Navigate the SIRIUS codebase

~90 Gradle modules and several thousand Java files. Grepping the tree is usually the slowest and
least reliable option. Two better instruments, with different strengths:

| Question | Best instrument |
|---|---|
| Where is `X` defined? Who calls it? What breaks if I change it? | **IntelliJ MCP index** (live, AST-accurate) |
| What modules exist, what is in them, what depends on what? | **Code map** (breadth, works without the IDE) |

## The IntelliJ MCP index

**Symbol or string?** A symbol (type, method, field) → the index. A string (an annotation, a TODO,
anything in `build.gradle` / `.properties` / `.md`) → plain search; the index does not cover it.

| Question | Tool |
|---|---|
| Where is `X` declared? What types are named `…`? | `search_symbol` |
| What does this call resolve to — overload, inherited, **Lombok**? | `get_symbol_info` at line/column |
| Who calls this? Blast radius of a change? | `analyze_calls` |
| Did my Java edit break anything? | `get_file_problems`, `lint_files` |
| Rename a symbol repo-wide | `rename_refactoring` — not grep + sed |

The index resolves inheritance, overloads and Lombok-generated members that do not exist in the
source text — grep cannot see any of those. But `search_symbol` matches **declared identifiers
only**: it does not list Lombok members either, so a miss there is not evidence the member is absent
— resolve it at a call site with `get_symbol_info`. `search_symbol` also indexes
`build/generated/**`; pass `paths: ["!**/build/**"]` to keep build output out of the results.

The index is not only for reading: `rename_refactoring` updates every reference from the AST — Lombok
accessors, `@Builder` methods and method references included — while leaving same-named members of
unrelated types, and the same word in a comment, untouched. `sed` cannot do that. Two things to expect:
the reported count is usages of the *renamed symbol*, so a Lombok-backed field reports 0 even though
its accessor call sites are updated; and it can reformat the lines it touches to IDE code style, so
read `git diff` before committing. Rename is the only refactoring exposed — no extract, inline, move or
change-signature. For runtime rather than structural questions, see the `debug-sirius` skill.

It is not always available (the server may be disconnected). Fall back to the code map plus search
tools, and say which one you used when it affects confidence in the answer.

## The code map

Generated by `./gradlew aiOverview -q` — a pure source parse, no compile, of `src/main/java` only. Test
sources are never in it, and a module whose only Java lives under `src/test/java` does not appear at all,
so a module you know exists can be legitimately missing. Output is **gitignored** under
`build/ai-overview/`. If it is missing, see first-time setup in the root `AGENTS.md`.

```
build/ai-overview/
├── index.md                   # every module with src/main/java + type count + link to its map
├── module-dependencies.md     # project→project dependency graph
└── modules/
    ├── <module>.md            # public/protected types & signatures
    └── <module>/              # large modules split per package
```

**Large modules are split, and then `<module>.md` holds only a package index** — the types live in
`<module>/<package>.md`. Grepping `modules/chemistry_base.md` for a type it certainly contains
returns nothing, which looks exactly like the type not existing. Grep `build/ai-overview/` whole.

**It can lag the working tree.** Being gitignored, it only regenerates when someone runs `aiOverview`
or has the opt-in git hooks, and its header shows the commit it was generated at rather than the
current one — so the stamp tells you nothing. Compare mtimes instead: Gradle leaves the outputs alone
when the task is up to date, so `index.md`'s mtime is the last real generation.

```bash
# 0 => current. Catches uncommitted edits too. ~0.05 s over ~2,800 files.
find . -path ./build -prune -o -path '*/build' -prune -o \
     -name '*.java' -newer build/ai-overview/index.md -print | wc -l

./gradlew aiOverview -q      # the fix; ~5 s, and a no-op when nothing changed
```

A `0` means the **type maps** are current. It says nothing about `module-dependencies.md`, which comes
from `build.gradle` project→project edges — re-run the task after changing one. A branch switch can
refresh every mtime and read as stale, which is the harmless direction.

### Picking the right module, and blast radius

`module-dependencies.md` is the fastest source for project→project edges. For each module it lists:

* **direct dependencies grouped by configuration** — `api` = re-exported to consumers (changing it
  propagates), `implementation` = internal to that module (safer to change);
* the reverse **`used by`** set — read this as the **blast radius** of a change.

`used by` is the **last** bullet of a module's block, and each bullet above it is a single line that
can run to a thousand characters. A line-capped or `-A N` read drops it silently, which looks
exactly like a module with no consumers. Read the whole block before concluding anything is unused.

Only project→project edges are here. External libraries are deliberately excluded — for those see
the `analyze-gradle-dependencies` skill.

### Reading a per-module map

Members tagged **`(lombok)`** (`getX`/`setX`/`builder`/…) are *inferred* by the generator, because
Lombok generates them at compile time and they are absent from the source. Treat them as "very
likely present"; the IntelliJ index resolves them exactly.

### More detail on demand

Off by default because it costs tokens. Turn on only when signatures alone are not enough:

```bash
./gradlew aiOverview -q -PaiOverview.classDocs=full        # whole class descriptions
./gradlew aiOverview -q -PaiOverview.methodDocs=summary    # or =full — method javadoc
```

`classDocs` defaults to `summary`, `methodDocs` to `none`.

## Suggested order of attack

0. Is the map current? Run the mtime check above — once before you start relying on it, and again
   after you edit Java yourself.
1. `index.md` — which module plausibly owns this?
2. `module-dependencies.md` — is it upstream or downstream of what I am changing? Who else uses it?
3. The per-module map — exact types and signatures.
4. The IntelliJ index — precise definitions, usages and call graphs before editing.
5. Plain search — last resort, or for non-Java assets (resources, `build.gradle`, configs).
