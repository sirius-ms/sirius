# Regenerate the SIRIUS SDK after a REST API change

`:sirius-sdk:sirius-sdk.openapi` is **generated code**, produced from an OpenAPI spec that is
itself generated by booting the REST service and scraping `/v3/api-docs`. A REST change that
is not followed by regeneration compiles fine but leaves the SDK — and every SDK consumer,
including the Swing GUI and the JS monorepo — silently stale.

**Always report an API break.** Any change to an existing operation — a new or optional parameter, a
renamed operationId, a changed type — is reported to the user, and recorded in the MR and the CHANGELOG.
A deliberate break is fine; a silent one is not, and a shim that keeps callers compiling does not make
it silent.

## The coupling

```
:sirius_rest_service controller/DTO change
        ↓  bootJar + forked Boot run on :8888, scrape /v3/api-docs
   sirius_rest_service/openapi-spec-enums-as-ref.json
        ↓  openApiGenerate  (registered on :sirius-sdk, NOT on the .openapi child)
   sirius-sdk/sirius-sdk.openapi/                   (generated Java sources)
        ↓
   consumers: Swing GUI, ../sirius-js-monorepo
```

**This is a cycle.** `:sirius_rest_service` depends on `:sirius_gui` (`implementation`), which depends
on `:sirius-sdk` (`api`), whose sources are generated from the spec that only a running
`:sirius_rest_service` can produce — `forkedSpringBootRun` `dependsOn :sirius_rest_service:bootJar`,
and that bootJar compiles `:sirius_gui` and the generated SDK. Gradle never reports it, because the
back edge is code generation rather than a project dependency.

It bites in a specific order. Step 1 succeeds, because the GUI still compiles against the *old* SDK.
**Step 2 is what breaks the GUI** — the members it calls have just been renamed or removed — and from
then on everything needing `bootJar` fails: step 1 and step 6. What you see is
`Execution failed for task ':sirius_gui:compileJava'` with every error path under `sirius_gui/`, while
the SDK modules are listed `UP-TO-DATE` just above and the task you actually invoked is never
mentioned — it simply never runs. The pointer back to the real cause is the compiler's `location:`
line, which names the SDK type the missing member belongs to.

## Steps

1. **Regenerate the spec.** This starts a real Boot server on port 8888 via
   `forkedSpringBootRun` (which `dependsOn :sirius_rest_service:bootJar`), so it is slow and
   needs the port free:

   ```bash
   ./gradlew :sirius_rest_service:generateOpenApiDocs -q
   ```

   Writes `sirius_rest_service/openapi-spec-enums-as-ref.json` — the spec the Java SDK uses.

2. **Regenerate the SDK.** Note the task lives on `:sirius-sdk` and writes *into* the
   `sirius-sdk.openapi` child module:

   ```bash
   ./gradlew :sirius-sdk:openApiGenerate -q
   ```

   Config: `sirius-sdk/build.gradle` (`openApiGenerate {}`) + `sirius-sdk/openapi-gen-config.json`;
   a `licenseInfo.mustache` template override in `sirius-sdk/templates`. Packages are
   `io.sirius.ms.sdk.{api,client,model}`.

3. **Fix the `:sirius_gui` call sites by hand.** A breaking change leaves the GUI calling SDK members
   that no longer exist. This is ordinary editing work, not generation — nothing regenerates the GUI.
   Until it compiles, anything needing `bootJar` stays broken.

   ```bash
   ./gradlew :sirius_gui:compileJava -q     # the fast signal while fixing
   ```

4. **Check what the change did to the published client surface.** Every generated client — the Java SDK
   here, the JS monorepo, the Python and .NET clients — comes from the same spec, so this is a spec-level
   question and needs none of them present:

   ```bash
   git diff sirius_rest_service/openapi-spec-enums-as-ref.json
   git diff -U0 sirius-sdk/sirius-sdk.openapi/src/main/java/io/sirius/ms/sdk/api/ | grep '^-.*public '
   ```

   A new operation is safe. A change to an existing one is not — an added parameter counts even when it
   is optional. Put the previous signature back as a deprecated delegate in the hand-written classes
   beside the generated API, so existing code compiles for one more release.

5. **Compile.** `:sirius-sdk:build` builds no consumer, so use the REST service to prove the change
   actually lands:

   ```bash
   ./gradlew :sirius-sdk:build -q
   ./gradlew :sirius_rest_service:bootJar -q   # this is what catches GUI breakage
   ```

6. **Verify against a live server.** SDK integration tests boot the real service
   (`integrationTest` there `dependsOn :sirius_rest_service:bootJar`):

   ```bash
   ./gradlew :sirius-sdk:sirius-sdk.openapi:integrationTest -q
   ```

## The other two spec variants

Three specs are generated, and **step 1 only refreshes the first**. Regenerate the variant
your change affects — each is `finalizedBy generateOpenApiDocs`, so it also refreshes the
ref-based spec:

| Task (`:sirius_rest_service:…`) | Output spec | Consumer |
|---|---|---|
| `generateOpenApiDocs` | `openapi-spec-enums-as-ref.json` — **tracked** | Java SDK (`:sirius-sdk`) |
| `generateOpenApiDocsEnumsAsString` | `openapi-spec-enums-as-string.json` — **tracked** | compatibility clients; feeds `updateUnstableExclusions` |
| `generateOpenApiDocsAdvancedEnumsAsString` | `openapi-spec-advanced-enums-as-string.json` — **gitignored** (`sirius_rest_service/.gitignore`) | the JS monorepo |

Only the first two are checked in. The advanced variant is generated on demand for the monorepo, so
expect it to be absent or stale in a fresh clone — and do not try to commit it.

## If the change must reach the React views

The React code lives in a **separate repo**, `../sirius-js-monorepo` (override with the
`siriusJSMonorepo` Gradle property). Push the spec across, then pull the built app back:

```bash
./gradlew :sirius_rest_service:copyOpenApiDocsToMonorepo -q   # spec → JS monorepo
# regenerate the JS client + build the app inside sirius-js-monorepo
./gradlew :sirius_rest_service:copyJSAppToFrontend -q         # built app → src/main/resources/templates
```

Both tasks are no-ops if the monorepo is not checked out next to this repo — do not treat
their silence as success.

## Traps

* **An optional parameter is not automatically a compatible change.** The HTTP route survives it; a
  generator that emits positional signatures — Java among them — changes the method and breaks callers
  at compile time.
* **`ApiBackwardCompatibilityTest` will not catch that.** It asserts against the committed spec, not
  against generated method signatures.
* **Wrong task path.** It is `:sirius-sdk:openApiGenerate`. There is no `openApiGenerate` on
  `:sirius-sdk:sirius-sdk.openapi` — that module only *receives* the output.
* **Generated code is not hand-editable.** Never edit under `sirius-sdk/sirius-sdk.openapi/src`;
  change the controller/DTO, the templates, or `openapi-gen-config.json` and regenerate.
* **Once step 2 has run, step 1 is unavailable** until the GUI compiles again — spec generation needs
  `bootJar`, which needs `:sirius_gui`. If the spec needs another pass, fix the GUI first.
* **A green `:sirius-sdk:build` says nothing about the GUI.** It schedules no `:sirius_gui` or
  `:sirius_rest_service` task at all, so breakage there is invisible at that step. It does cover the
  SDK's own tests, so a green run there is not worthless — just not evidence about consumers.
* **Port 8888 must be free**, or spec generation hangs/fails.
* **Commit the spec, the regenerated SDK sources and the `:sirius_gui` fixes together with the REST
  change** — all four are one change. A spec that disagrees with the controllers, or an SDK the GUI
  cannot compile against, leaves the next person unable to tell which side is authoritative.
* Review the spec diff (`git diff sirius_rest_service/openapi-spec-*.json`). An unexpectedly
  large diff usually means a DTO leaked an internal domain type into the API surface.
